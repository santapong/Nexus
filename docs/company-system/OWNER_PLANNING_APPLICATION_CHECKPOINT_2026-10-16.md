## Product behavior

One configured Nexus goal follows explicit bootstrap proposal → owner r1 approval
→ protected preparation → exact input review and action decision → atomic dispatch
→ status/historical candidate → formal same-root revision → owner approval. Reads
and decisions cannot choose an actor, provider, allowance or queue. A candidate is
not approved work. Unconfigured legacy/input-only profiles retain their boundaries.

The concrete lifecycle loads the actual stored approved r1. Both management and
planning service bundles retain the same instance, factory, source catalog, stores
and native services. It does not manufacture a base plan or swap readers between
UI steps. A private, bounded, hash-pinned configuration selects one supervised goal.

Explicit API, worker and migration modes preserve the genuine configured signer
and finite actor-credential source. Minimal boot checks the restricted schema and
durable runtime, leaving fresh actor/model eligibility at its actual effect gates.
Historical issued replay can work after fresh model credentials expire. Startup
creates no company, account, goal, mandate, charter, plan, approval or qualification.
The original host executor owns DBOS retirement after the SDK adopts its own pool.

## Interrupted preparation

Explicit recover-wait only restores the exact saved pending action's unissued
await-approval state. Current owner/actor/source access, original cutoffs, Goal/head,
immutable body and native snapshot CAS remain mandatory. Live/ambiguous/issued/
held/dispatched or used/delegated prefixes deny. An existing exact wait is a replay.
Recovery does not reset time, budget or counters, create a new request or issue SDK
work. Protected reads happen outside the outer company-control transaction; actual
read and transition owners remain retained through cancellation.
